## 1. 要解決的問題

`ios-dev` 是給 iOS 工程師用的：它在開發前定架構、列 test cases、派審查 agent，最後由人讀 diff 核准。整條流程裡有 81 個地方會停下來問人，其中 50 個用工程語言問（檔名、SwiftUI API、review 路線），只有 17 個是產品問題。

vibe coder 不讀 code。把 `ios-dev` 直接交給他，會卡在兩處：

1. **聽不懂問題**：他分不出「先用 `swiftui-view-refactor` 拆，還是直接加」要怎麼選。
2. **做不到最後一關**：`ios-dev` 的終點是人工 code review，他讀不懂 diff。

`ios-vibe` 的承諾是**看不見的護欄**：背後照跑 `ios-dev` 的整套檢查，使用者只會在兩種時候被打擾——需要他做產品決定，以及請他試用成果。

### 目標使用者

- **主要**：不讀 code 的人，例如設計師、PM、想做 app 的創業者。只看畫面對不對、會不會閃退。
- **次要**：會寫程式但不熟 iOS 的工程師，例如寫 Web 或 Android 的人。

判斷準則不是背景，是「他會不會讀 AI 改的 code」。

### 成功的樣子

- 使用者從零做出一個 app，裝到自己的 iPhone 上。
- 整個過程中，他被問到的問題裡，需要懂工程名詞才答得出來的是 0 個。
- 每次改完，他拿到一張試用卡：最多 5 步的實機試用，試完回「OK」。

## 2. v1 不做的事

- **TestFlight 與 App Store 送審**：需要付費開發者帳號、憑證與 `asc-*` 系列 skill。留到 v2。
- **在「主力是 Codex」時提供跨模型審查**：v1 只做「Claude 寫、Codex 審」這個方向（§8）。
- **自動化評測（evals）**：先真人實測、知道失敗長什麼樣，再寫評測（§14）。
- **教學模式**：只在出事時附一句白話原因，不另開教學流程。
- **多語系與譯者複核**：`localize-strings` 屬於出貨階段，v1 不主動觸發。
- **vibe 版把關不了的功能**：帳號登入、付款與訂閱、需要連網才能運作的功能（呼叫後端或第三方 API、跨裝置同步）、敏感個資（健康、財務、精確位置、聯絡人，以及把相簿內容上傳到任何地方）。這些功能出錯的後果，試用卡測不出來，同一個模型的審查也擋不住。使用者要求時直說「這超出 vibe 版能安全把關的範圍」，並給兩條路：改成只存在手機裡的版本，或找工程師接手（§5「超出範圍的需求」）。

- **破壞性的資料格式變更**：改名、刪欄位、改型別、拆開或合併資料種類。這類變更失敗時資料救不回來；v1 只允許資料框架能自動升級的「新增」類變更，並有自動備份當退路（§7「資料格式升級與退路」）。

v1 支援的是**資料只存在這支手機上的 app**。範圍內仍有使用者試不出來的風險：存資料、新增類的格式升級、刪除、權限、背景工作。這幾種改動改由強制的自動化測試守住（§6「高風險改動的強制測試」）。

## 3. 架構：薄包裝層

```
使用者 ──白話──▶ ios-vibe ──照跑──▶ ios-dev（Step 0–8）──▶ 下游 skill／審查 agent
                   │
                   ├─ 攔截 ios-dev 每個「停下來問人」的點（§4）
                   ├─ 管版本存檔（§7）
                   └─ 產出試用卡（§6）
```

- `ios-vibe` **不複製** `ios-dev` 的流程。`ios-dev` 改版後，一般的問人點由四條規則自動接住；硬關卡的遺漏分兩層抓（§4「接觸點標記與檢查」）：接觸點標記加關鍵字檢查擋下大部分，換了說法漏抓的，再由執行期紀錄在實際跑的時候抓到。**兩層都是盡力而為，不保證零遺漏。**
- `ios-vibe` 只存在本 repo，沒有另一份上游要同步。
- **衝突時的優先序**：`ios-vibe` 與 `ios-dev` 衝突時以 `ios-vibe` 為準，但**只限 §4 例外表列出的點**。例外表沒列的 `ios-dev` 規則一律照舊，包括所有審查 agent、風險三條與輕重判斷。

### 和「共用策略」做法的比較

Codex 第 1 輪審查提出另一種做法：在 `ios-dev` 與 `phase-workflow` 的每個接觸點都去查同一份策略檔，工程師版和 vibe 版只是兩組不同的設定。兩者比較：

| | 包裝層＋標記與檢查（採用） | 共用策略 |
|---|---|---|
| `ios-dev` 要改的 | 每個接觸點加一行註解標記，描述這個點本身的性質 | 每個接觸點改寫成「查策略檔再決定怎麼做」 |
| 維護者改 `ios-dev` 時 | 新增問人點要加標記；忘了加，檢查會報錯 | 每次都要同時想兩組設定的行為 |
| 新增硬關卡被漏掉 | 關鍵字檢查擋下大部分；漏抓的由執行期紀錄在實際跑的時候抓到 | 沒經過共用接口的新接觸點可以預設失敗，偵測比較完整 |
| vibe 版的規則放哪 | 集中在 `ios-vibe` | 分散在策略檔與各接觸點 |

共用策略在「偵測遺漏」上比較強。採用包裝層，是拿這一點換 `ios-dev` 的單純，原因和 Q5 相同：不讓 `ios-dev` 每次改版都得同時考慮兩種模式。標記描述的是接觸點本身的性質（它問的是工程還是產品問題），不是 vibe 版的處理方式，對 `ios-dev` 本身也有用。

### 進場方式

- 明確呼叫才進場：Claude 用 `/ios-vibe <想做什麼>`，Codex 用 `$ios-vibe`（Codex 不支援帶參數的 slash 呼叫）。
- `install.sh --vibe` 會先徵求同意，再在全域設定寫一段「這台電腦的 iOS 需求預設走 `ios-vibe`」：Claude 寫進 `~/.claude/CLAUDE.md`，Codex 寫進 `~/.codex/AGENTS.md`。這段有起訖標記，`--uninstall` 會移除。
- 不靠 description 自動判斷，避免和 `ios-dev` 互搶同一句「幫我加一個匯出功能」。

### 語言

skill 本身用繁中寫，和本 repo 一致。回覆跟著使用者的語言。

## 4. 人類接觸點：四條規則加一張例外表

### 四條規則

1. **工程決策由 AI 採推薦答案**，並記進使用者專案的 `docs/vibe-decisions.md`。之後 app 交給工程師接手，他看得到哪些是 AI 替使用者決定的。
2. **產品決策翻成白話問**，一次最多 3 題。問題必須在不懂任何工程名詞的情況下答得出來（§14 的驗收標準）。
3. **需要人看 code 的點，換成試用卡**（§6）。
4. **需要使用者打指令或開新 session 的點**，由 AI 在同一個 session 做等價的事，或避開那條路。

**混合題拆開處理**：工程那一半照規則 1，產品那一半照規則 2。例如：

- Step 5 列 test cases：測試函式名由 AI 定；邊界情況的預期行為（「相簿裡一張照片都沒有時按匯入，應該怎樣？」）問使用者。
- `ios-review` 的批次詢問：concurrency、架構類由 AI 採建議修法；「會移除功能」「會改變使用者看到的行為」這兩類問使用者。
- 優化情境的驗收數字：範圍由 AI 推斷；「多快才算夠」問使用者（「現在大概卡幾秒？希望變成怎樣？」）。

### 例外表

四條規則處理不了、或會和 `ios-dev` 硬規則衝突的點，逐條列在這裡。實作時放進 `skills/ios-vibe/references/touchpoint-rules.md`，每一列補上接觸點編號（編號在階段 1 加標記時產生，見下方「接觸點標記與檢查」）。

**A. 原本要使用者打指令或開 session**

| ios-dev 的點 | vibe 版怎麼做 |
|---|---|
| Step 0 前置：請使用者跑 `setup-matt-pocock-skills` | 不跑。vibe 版不用 mattpocock 的訪談工具 |
| Step 3：請使用者輸入 `/grill-with-docs` | 改用 vibe 版自己的白話訪談（§5）。不產 `CONTEXT.md`、`docs/adr/`，決策記進 `docs/vibe-decisions.md` |
| 交棒 `phase-workflow`：印指令、建議開新 session | 同一個 session 執行（§5「同一個 session 跑 phase-workflow」） |
| 每張 ticket 開新 session 接手；做完問「接下一張？」 | 同一個 session 依序做，不問、直接接下一張（§5「同一個 session 跑 phase-workflow」） |

**B. 原本要人看 code**

| ios-dev 的點 | vibe 版怎麼做 |
|---|---|
| 人工 code review 不可省（三條 review 路線的終點） | 換成試用卡，卡上固定聲明「沒有人類讀過這份 code」。**這是 vibe 版最大的一條覆寫**，必須明講，不可淡化 |
| 路線 B／C：使用者讀完 diff 口頭確認 | 使用者對試用卡回「OK」 |
| 路線 A：人工執行 `approve-code` | vibe 版不走路線 A，所以不會出現這一步。設定 b 改用唯讀跨模型審查（§8），終點是試用卡。`approve-code` 代表「讀過 code 的人核准」，使用者試用後的 OK 不能拿來代替 |
| 情境 7：停下來等使用者讀 diff | 同上，換成試用卡 |
| 實作和架構約定對不上，判斷不出是實作錯還是約定不適用 | 一律先修實作。修不了，才翻成產品問題問使用者（「要做到這件事，得改變 X 的行為，可以嗎？」）。**不准改約定去遷就 code** |

**C. 產品判斷：保留，但換成白話**

| ios-dev 的點 | vibe 版怎麼做 |
|---|---|
| Step 3 出口：使用者確認需求摘要 | 保留。用 3 句白話複述「我要做的是……」請使用者確認 |
| 答案不清楚時必須停下來問 | 保留 |
| `office-hours` 的「誰需要、現在怎麼解決、只做一個做什麼」 | 併進從零開始的 5 題（§5） |
| `office-hours` 的「範圍需要主管確認」 | 不適用（個人專案） |
| `office-hours` 完成時確認 design doc | 改成確認 MVP 清單：最多 3 個畫面，各一句話 |
| `ios-investigate` 問重現步驟、發生頻率、裝置 | 保留，白話問：「你做了什麼、多常發生、用哪支手機」 |
| 缺資訊時說明需要什麼（`NEEDS_CONTEXT`） | 保留，白話 |
| `phase-workflow` 入口 B：貼 GitHub issue、挑 sub-issue | 不適用。vibe 版不走 PM spec 入口 |

**D. 硬關卡：原本不一定問人，但 vibe 版要改掉的規則**

| ios-dev 的規則 | vibe 版怎麼做 |
|---|---|
| Step 0 一定要出確認畫面、確認一次 | 不出確認畫面。AI 內部照算整組 bundle，採選項 1（「照這組跑」），把組合記進 `docs/vibe-decisions.md`；試用卡列出實際派了哪些審查 |
| Step 7：計畫文件沒經 `consensus-plan`（Codex 唯讀審查）不准開始實作 | 改由同一個 AI 派 sub-agent，以「對照既有 code」的角度審一次計畫，AI 依意見自己改完就開做 |
| 情境 1（沒有 PM spec）交 `phase-workflow` 切 ticket，每張 ticket 開新 session 由使用者接續 | 照樣交 `phase-workflow` 規劃與切 ticket，**只覆寫「開新 session」與「使用者手動接續」**（§5）。仍是情境 1，審查強度維持重 |
| 複雜 bugfix 強制走路線 A | vibe 版不走路線 A，改依使用者的審查設定（§8）：選 b 時走路線 B 再加唯讀跨模型審查；選 a 時走路線 B，試用卡註明「這是比較複雜的修正，只有同一個 AI 審過」 |
| 人工核准前不得 commit | 工作分支上可以自動存 local commit；併回主線、push 仍要等使用者說 OK（§7） |

### 接觸點標記與檢查

例外表用步驟名稱指向 `ios-dev` 的規則，`ios-dev` 改版時很容易對不上，而且不會有任何警告。所以接觸點要有穩定的編號，並用腳本檢查。

**標記**：在 `ios-dev`、`phase-workflow` 與它們會交棒的下游 skill 裡，每個停下來問人或等人的地方加一行註解：

```markdown
<!-- touchpoint: ios-dev-007 kind=gate -->
```

- 編號格式是 `<skill 名稱>-<三位數序號>`。編號一旦給出就不改，步驟改名或搬位置都沿用。
- `kind` 描述這個接觸點本身的性質，不描述 vibe 版怎麼處理：

| kind | 意思 | vibe 版預設怎麼處理 |
|---|---|---|
| `engineering` | 問工程決策 | 規則 1 |
| `product` | 問產品決策 | 規則 2 |
| `mixed` | 兩者混合 | 拆開，分別套規則 1、2 |
| `code-review` | 要人看 code 或 diff | 規則 3 |
| `command` | 要使用者打指令或開 session | 規則 4 |
| `gate` | 硬關卡：不一定問人，但規定「沒做到就不准往下」 | **一定要在例外表有一列** |

**例外表**：每一列都寫上它對應的接觸點編號。預設處理不適用的點（例如 `office-hours` 的「範圍需要主管確認」在 vibe 版不適用），不論 kind 都列進例外表。

**檢查腳本** `skills/ios-vibe/scripts/check-touchpoints.py` 檢查四件事，任何一件不過就報錯：

1. **有沒有漏標**：在上述 skill 裡找疑似接觸點的句子（`AskUserQuestion`、「詢問」「暫停」「停下來」「STOP」「等使用者」「確認後才」「人工」「不得 commit」等），附近沒有標記就報錯。誤判的句子可以加 `<!-- touchpoint: none -->` 註明不是接觸點。
2. 每個標記的 `kind` 都是上表六種之一，編號沒有重複。
3. 每個 `kind=gate` 的標記，在例外表都有對應的一列。
4. 例外表的每一列都指向一個真實存在的標記。

這支腳本和現有的 `validate-router.py` 一起跑，列進 README 的本機檢查清單。標記要跟著 §14 階段 5 一起同步回上游。

**關鍵字檢查是盡力而為**：擋得住大部分遺漏，但新增的接觸點只要換個說法就會漏抓，四項檢查照樣全過。所以另外加執行期紀錄。

**執行期紀錄**：`ios-vibe` 規定 AI 每次向使用者提問、或停下來等使用者回覆時，都在專案的 `.vibe/touchpoint-log.jsonl` 記一行：時間、接觸點編號、問題原文，以及這題有沒有用到工程語言（AI 自評）。對不上任何編號時，編號記成 `unmapped`。

- `check-touchpoints.py --log <路徑>` 讀這份紀錄：出現 `unmapped` 就代表某個接觸點漏標，要回頭補標記或補例外。
- 三次實測結束時各跑一次。紀錄是 AI 自己寫的，可能漏記，所以實測時作者要拿對話紀錄對一次，確認每個提問都有記到。
- `.vibe/` 列進範本的 `.gitignore`，不進使用者的版本紀錄。
- 之後補自動評測（§2）時，直接吃這份紀錄。

## 5. 使用者旅程

### 從零開始

1. **白話訪談，一輪、最多 5 題**：
   1. 這個 app 給誰用？
   2. 他最常用它做的一件事是什麼？
   3. 打開 app 第一個看到的畫面長什麼樣？
   4. 關掉 app 再打開，資料要不要還在？
   5. 有沒有想參考的 app？
2. **定出 MVP**：最多 3 個畫面，各一句話說明。請使用者確認。
3. **建專案**：從本 repo 附的範本複製（§12）。
4. **規劃與實作**：維持 `ios-dev` 的情境 1（新專案）。5 題的答案與 MVP 清單當成 `phase-workflow` 入口 A 的輸入，照下方「同一個 session 跑 phase-workflow」做完；架構形狀照 `ios-dev` Step 4，審查固定走重（6 個審查 agent 加 `review-swarm`）。
5. **第一次裝到 iPhone**：第一張會出試用卡的 ticket 完成時，帶使用者第一次裝（§9）。

使用者只感覺得到「做得很快」，背後的規劃、切分與審查強度都和工程師版的新專案一樣。

第 4 題（資料要不要留著）刻意放進 5 題裡。不先問，之後補存資料的功能會踩到 `ios-dev` 的風險三條，改動變重。

### 加功能

每加一個功能都當情境 2：白話訪談一輪、最多 3 題 → 實作 → 試用卡。

### 碰到會動到 app 骨架的改動

`ios-dev` 判出「模組邊界」時（新增模組、多畫面流程、多個非同步工作要協調），原本會交給 `phase-workflow`。vibe 版：

1. **先提一個不動骨架的小版本**，用產品語言講，例如「先做只能匯出 CSV 的版本？」
2. 使用者要完整版，就照下方「同一個 session 跑 phase-workflow」做。這裡的 ticket 審查強度照 `ios-dev` 的五條件逐張判，不像從零開始那樣固定走重。

### 同一個 session 跑 phase-workflow

「從零開始」與「碰到骨架」共用這一套。`phase-workflow` 原本負責的規劃與切 ticket **照舊**，vibe 版只拿掉 vibe coder 做不到的兩件事：開新 session，以及由使用者手動接續下一張。

1. **規劃**：`phase-workflow` 入口 A 在同一個 session 跑完，根文件與 ticket 寫進專案的 `docs/features/<功能>/`。
   - 根文件審查原本交 `consensus-plan`，改由同一個 AI 的 sub-agent 做（§4 D）。
   - 中途的 STOP（確認大綱、確認 stage 數、要不要展開）都是工程決策，照規則 1 由 AI 採推薦答案。
2. **告知一次**：「我會分成 N 步，其中 M 步做完你可以試。」N 是 ticket 數，M 是會改變使用者看得到行為的 ticket 數。
3. **每張 ticket 照 `ios-dev` 情境 7（接 ticket）的完整流程**，順序固定：
   1. 讀 ticket、根文件對應段、實作紀錄
   2. `writing-plans` 寫這張的計畫；計畫審查照 §4 D
   3. `subagent-driven-development` 實作，TDD：先寫會失敗的測試
   4. 實作完成後重判風險（風險三條，情境 7 另加規模兩條）；從零開始的 ticket 一律重
   5. 依審查強度派審查 agent、統一修復，再照使用者的 a／b 設定走 review 路線（§8）
   6. §6 的強制測試與 UI 測試全部通過
   7. 存一個存檔點（§7）
   8. **行為類 ticket**（`phase-workflow` 的 Behavior）出試用卡，等使用者回 OK；**地基類 ticket**（Foundation、Prefactor）使用者試不出任何東西，只存檔、不出卡，在下一張試用卡的「做了什麼」補一句
   9. 回寫 ticket 狀態與實作紀錄，直接接下一張，不問「接下一張？」
4. **併回主線**：使用者對某張試用卡回 OK 時，這張連同它之前的地基類 ticket 一起併回（§7）。

同一個 session 做完多張 ticket，對話會變長、觸發自動壓縮。ticket 與實作紀錄都寫在檔案裡，壓縮後讀檔接續。

### 修 bug

照 `ios-investigate` 的流程，只把「問重現步驟」翻成白話。找到原因、修好之後，試用卡要寫清楚「原本會怎樣、現在應該怎樣、請你照原本出問題的步驟再試一次」。

### 超出範圍的需求

使用者要的功能落在 §2「vibe 版把關不了的功能」時，不開做，先直說：

> 「這個功能（例如：用帳號登入、把資料同步到另一支手機）出錯時，你試用時看不出來，我這邊的檢查也擋不住，超出 vibe 版能安全把關的範圍。有兩條路：
> 1. 先做只存在這支手機裡的版本（例如：資料只存在手機上，之後再請工程師加同步）
> 2. 這個功能找工程師接手，我把目前 app 的狀況整理給他」

使用者選 1，照一般的加功能流程做；選 2，把 `docs/vibe-decisions.md` 與目前的功能清單整理成一頁交接說明。不提供「你堅持就做，後果自負」這個選項。

## 6. 試用卡

### 分工

| 誰 | 做什麼 |
|---|---|
| AI | build、跑測試（含自動點過主要流程的 UI 測試）、截改前改後的圖 |
| 使用者 | 只有實機試得出來的部分（相機、麥克風、本機通知、震動回饋、手感），以及「這是不是我要的」 |

AI 做得到的驗證不交給人。沒有 iPhone 的使用者，試用步驟改在模擬器上做。

### 高風險改動的強制測試

人工 code review 原本會擋下的風險裡，有一類使用者用手試不出來。v1 已經把連網、登入、付款、敏感個資排除在範圍外（§2），範圍內剩下五類。改動碰到其中任何一類，AI 一定要補上對應的自動化測試，測試全過才出試用卡：

| 改動碰到 | 一定要有的測試 |
|---|---|
| 存資料 | 寫入後重建儲存層（模擬關掉 app 再打開），資料一致；只經由 §7「唯一的儲存方式」寫入（`check-boundaries.py` 檢查） |
| 新增欄位或資料種類（只允許這類，§7） | 用上一版格式的資料當輸入，升級後一筆都不少、內容正確；升級前的自動備份存在，還原後資料等於升級前 |
| 刪除 | 只刪到該刪的那筆；刪除要不要確認、能不能復原，是產品決策，照規則 2 問使用者 |
| 權限（相機、麥克風、相簿、通知等） | 使用者拒絕權限時不閃退，並顯示說明與前往設定的路徑 |
| 背景或同時進行的工作 | 取消、重複觸發時不寫壞資料（`concurrency-auditor` 照 `ios-dev` 規則也會派） |

### 主要流程的 UI 測試與不連網檢查

強制驗證不依賴任何選配工具，兩個平台、每種工具組合都做得到：

- **UI 測試**：每個行為類改動，AI 都把主要流程寫成專案 UI 測試 target 裡的 XCUITest，用 `xcodebuild test` 在模擬器上自動點過。不需要 MCP 或桌面 app。累積下來就是回歸測試，每張試用卡出之前全部重跑。
- **不連網，三層各擋一種洞**（v1 不允許連網，§2）。三層都是盡力而為，合起來也不等於證明 app 不會連網：
  1. **封閉的相依白名單**：v1 預設不准加任何第三方套件。要加，得先列進 `skills/ios-vibe/scripts/boundaries-allowlist.txt`，白名單一開始是空的。
  2. **執行期攔截**：範本在測試用的 build 裡註冊一個攔截所有網路請求的元件，UI 測試期間 app 只要發出任何請求，測試就失敗。每張卡出之前都會跑，是每張卡的關卡。
  3. **字串掃描**：`skills/ios-vibe/scripts/check-boundaries.py` 掃程式碼，抓執行期攔截攔不到的低階連線（`Network` framework、socket、WebSocket 等）。

  任何一層命中，都代表範圍被越過，照 §5「超出範圍的需求」處理。模擬器沒有飛航模式開關，不拿它做離線驗證。

MCP 與桌面 app 的模擬器面板，用來截圖、看畫面，也讓使用者能即時看著 app 被操作。它們讓體驗更好，但不是強制驗證的前提。

這些測試的名稱與結果**不出現在試用卡的操作步驟裡**，只在「檢查狀況」段落用白話列一句，例如「已確認：關掉再打開，資料不會不見」。

## 7. 版本與存檔

vibe coder 多半不會 git，只會說「回到剛剛能用的版本」。規則：

- **開工**：開一條工作分支 `vibe/<日期>-<簡稱>`。專案不是 git repo 時先 `git init`，範本建立時就做好。
- **工作區有使用者自己的未存改動**：不碰。白話問「有一些改動還沒存起來，要我先幫你存嗎？」
- **存檔點**：每到一個 build 成功、測試通過的狀態，就在工作分支自動存一次 local commit，commit 訊息寫白話。
- **回到上一版**：從目標存檔點開一條新分支繼續，舊分支保留。**不刪任何歷史**，不跑 `reset --hard`、`checkout --`、`restore`、`clean`、`stash drop`。
- **使用者說 OK**：併回主線。
- **push**：有遠端時一律先問；沒有遠端時不主動建議開 GitHub。

在有未 commit 改動的工作區跑 `git checkout --` 會直接丟掉那些改動，vibe coder 比工程師更容易踩到，這是「回到上一版不刪歷史」的原因。

### 唯一的儲存方式

備份要保證資料一致，前提是資料只存在一個地方。v1 規定：

- **所有 app 資料都存在 SwiftData**，資料庫放在固定的資料根目錄（Application Support 底下由範本指定的資料夾）。
- **使用者產生的檔案**（例如照片副本）也只能放在資料根目錄底下，透過範本提供的存取介面讀寫。
- **UserDefaults 只准存介面偏好**（例如上次停在哪個分頁），不備份，丟了也不影響使用者的資料。
- **禁止的儲存方式**：直接用 Core Data 或 SQLite、在資料根目錄以外寫檔、把使用者資料塞進 UserDefaults 或 Keychain。`check-boundaries.py` 會掃描；最後一項靠字串比對抓不完整，屬於盡力而為，由審查 agent 補看。

### 資料格式升級與退路

git 只退得回 code，退不回手機裡已經升級過的資料。所以資料格式的變更另有一套規則：

- **允許**：新增欄位（帶預設值）、新增資料種類，也就是資料框架能自動升級的類型。
- **不允許**：改名、刪欄位、改型別、拆開或合併資料種類。使用者的需求需要這類變更時，照 §5「超出範圍的需求」給兩條路：改成用新增欄位的方式做，或找工程師接手。
- **範本內建自動備份**：資料帶格式版本號。app 啟動時發現要升級，先關閉資料庫，把**整個資料根目錄**複製成以版本號命名的備份，再升級。資料庫檔、它的附屬檔與使用者產生的檔案都在根目錄裡，一次複製就一致。
- **跨過升級的「回到上一版」**：舊版 app 啟動時發現資料版本比自己新、讀不懂，就自動還原它那一版的備份。AI 在執行「回到上一版」之前先用白話講清楚：「退回去之後，升級以後新增的資料會不見。」使用者確認才退。
- **驗收**：§6 強制測試包含「備份存在、還原後資料等於升級前」；第 2 次實測刻意跨過一次升級做「回到上一版」（§14）。

## 8. 審查：同一個 AI，或再加另一個模型

| 設定 | 內容 |
|---|---|
| **a（預設）** | 由使用者正在用的 AI 派 sub-agent 審；`ios-dev` 的 review 路線固定走 B（純 agent） |
| **b（更仔細）** | 在 a 的審查之外，再加一次**唯讀跨模型審查**：Codex 只讀這次的改動、提出意見，Claude 依意見統一修一次。不走 `ios-dev` 的路線 A，沒有 `approve-code`，也不會停在「等人審 code」 |

- **什麼時候問**：第一次使用時問一次，記在 `docs/vibe-decisions.md` 開頭的設定區。之後只在高風險改動時再提一次 b：改到存資料的方式、會刪東西、要新的權限、改到同時進行的背景工作（也就是 v1 範圍內會踩到 `ios-dev` 風險三條的改動；連網已排除在範圍外）。提的時候講清楚多了誰在看、會多花時間。
- **b 的順序**：實作 → 審查 agent（a 的部分）→ Codex 唯讀審查 → 統一修復一次 → §6 強制測試與 UI 測試 → 存檔 → 試用卡。
- **b 只在一種環境提供**：主力是 Claude、而且裝了 Codex。主力是 Codex 時，找 Codex 審等於自己審自己，不是交叉審查；反方向（Claude 審 Codex 寫的）v1 不做。其他環境問的時候直接說明「你的環境只能用 a，因為……」。
- **b 的相依不在預設安裝**：Codex CLI 與登入，第一次選 b 時才帶著裝。實作時先查 `ai-review` 有沒有不帶 `approve-code` 閘門的唯讀 code 審查模式：有就用它；沒有就直接用 `codex exec` 在唯讀 sandbox 裡跑一次審查。
- **b 只作用在 code 審查**。計畫文件的審查在 vibe 版一律由同一個 AI 的 sub-agent 做（§4 D）。

## 9. 第一次裝到 iPhone

三件事 AI 不能代做，一步一步帶，每步等使用者回「好了」才走下一步；某一步失敗就原地排除，不往下走：

1. **在 Xcode 登入 Apple ID**：Xcode → Settings → Accounts → 加入 Apple ID。要輸入密碼，AI 不代勞。
2. **在 iPhone 打開開發者模式**：設定 → 隱私權與安全性 → 開發者模式，開啟後手機會重開機。前提是 iPhone 已經用線接過這台 Mac、按過「信任這部電腦」。
3. **第一次裝完後，在 iPhone 信任這個開發者**：設定 → 一般 → VPN 與裝置管理。

其餘由 AI 做：設定簽署團隊與 bundle id、build、用 `xcrun devicectl` 安裝。

VIBE.md 要先講清楚免費 Apple ID 的限制：裝上去的 app 大約 7 天後會打不開，要重新安裝。

## 10. 防呆：擋破壞性指令

- **Claude**：沿用 `careful-ios`（skill 裡掛的 PreToolUse hook），命中時問使用者。
- **Codex**：Codex 會忽略 skill 裡的 hook 設定。`install.sh --vibe` 把**同一支檢查腳本**註冊進 `~/.codex/hooks.json`（合併，不覆蓋既有內容），安裝引導多一步「在 Codex 輸入 `/hooks`，把它設為信任」。Codex 的 hook 只能擋下、不能先問，所以命中時一律擋下，由 AI 用白話說明原因，要不要執行由使用者自己決定。
- 檢查腳本加一個 Codex 輸出模式，兩個平台共用同一套判斷與測試。

不用 Codex rules 檔：它只比對指令前綴，`careful-ios` 原本放行的安全例外（清 DerivedData、Pods 這類快取）也會被擋。也不能只靠 Codex 的沙盒與核准機制：vibe coder 看到核准請求多半直接按同意。

## 11. Claude 與 Codex 雙平台

整個 repo 改成兩個平台都能用，不只 `ios-vibe`。`ios-vibe` 背後照跑 `ios-dev`，`ios-dev` 在 Codex 上跑不動，vibe 版也一樣跑不動。

### 現在在 Codex 上跑不動的地方

| 問題 | 改法 |

| 9 個審查 agent 是 Claude 的 `.md` 格式，Codex 只讀 `.toml` | agent 原稿維持一份 `.md`，由 `scripts/gen-codex-agents.py` 轉出 `.toml` 裝到 `~/.codex/agents/`。Codex 不能逐一限制工具，唯讀 agent 用 `sandbox_mode = "read-only"` |

`ios-vibe` 寫成「有哪個工具就用哪個」：

| 環境 | 工具 | AI 能做什麼 |

## 12. 專案範本

放在 `skills/ios-vibe/templates/app/`，AI 複製後改名。內容：

- 一個 SwiftUI app，加一個單元測試 target（Swift Testing）與一個 UI 測試 target（XCUITest）
- 使用新版 Xcode 的資料夾同步格式：新增或刪除檔案時不必改專案檔
- Swift 6 語言模式，打開嚴格並行檢查
- 最低 iOS 版本：最新正式版減一
- 專案層的 `CLAUDE.md` 與 `AGENTS.md`，寫明這是 vibe 專案、由 `ios-vibe` 管理
- 資料層：SwiftData 容器固定在資料根目錄、資料根目錄的檔案存取介面（§7「唯一的儲存方式」）
- 資料格式版本號、升級前自動備份，以及舊版遇到新格式時的還原機制（§7），附自己的測試
- 測試用 build 裡的網路請求攔截元件（§6），正式 build 不含
- 不含任何第三方套件
- `.gitignore`（含 `.vibe/`），以及建好後的第一個 commit

### 三次實測

| 次 | 平台 | 內容 |
|---|---|---|
| 1 | Claude 桌面 app | 從零做一個**會存資料、也能刪除資料**的小 app（例如記帳），裝到實機 |
| 2 | Claude 桌面 app | 在第 1 次的 app 上加一個功能，這個功能要**新增一個資料欄位**（例如記帳加分類），並用到一種權限；做完後刻意跨過這次升級做一次「回到上一版」 |
| 3 | 只有 Codex | 從零建一個小 app，再修一個故意放進去的 bug：**快速連點儲存，會存出重複的資料** |

三次的題目刻意涵蓋 §6「高風險改動的強制測試」的五類：存資料與刪除（第 1 次）、新增欄位與權限（第 2 次）、背景或同時進行的工作（第 3 次，重複觸發造成資料寫壞）。

- 作者自己跑的，每次都開**新的 macOS 使用者帳號**，完全照 VIBE.md 從零開始。這台電腦日常的 `~/.claude`、`~/.codex` 已經裝了很多 skill，會把缺的東西補上，測不出新使用者會卡在哪。

## 15. 風險與待驗證

| 風險 | 怎麼處理 |
|---|---|
| Codex 的系統提示要求「skill 的指示由主 agent 自己讀，不要交給 sub-agent 讀」，而審查 agent 開工時就是在讀另一個 skill 的檢查清單 | 第 3 次實測驗證。不行的話，改成由主 agent 讀檢查清單，把相關段落放進派 agent 的指示 |
| Build iOS Apps plugin 內含 `swiftui-ui-patterns`、`swiftui-view-refactor`、`swiftui-performance-audit`，和路由表引用的第三方 skill 同名 | 階段 3 比對內容是否相同，決定用哪一份 |
| Codex plugin（superpowers、Build iOS Apps）能不能用指令安裝，目前查不到 | 階段 3 查。不行就放進 VIBE.md 的引導步驟 |
| XcodeBuildMCP 的 UI 自動化功能組怎麼用設定打開 | 階段 1 查官方設定文件 |
| 同一個 session 做多張 ticket，對話變長、觸發自動壓縮 | ticket 與進度寫在檔案裡；實測時觀察壓縮後能不能正確接續 |
| 單一模型審查會漏掉什麼，目前不知道 | 使用者試不出來的風險，已經用範圍限制（§2）與強制測試（§6）先擋一層；三次實測後回頭看漏掉的，再決定要不要把 b 擴大到其他環境 |
| `ios-dev` 改版時新增問人點或硬關卡 | 兩層盡力而為（§4）：標記加關鍵字檢查擋下大部分；換了說法漏抓的，由執行期紀錄的 `unmapped` 抓到。執行期紀錄靠 AI 自己寫，實測時作者對照對話紀錄驗證 |
| 自動備份與還原機制寫在範本裡，它本身有 bug 就會連帶弄丟資料 | 範本的備份與還原有自己的測試；第 2 次實測刻意跨升級回退一次 |
| 不連網與唯一儲存方式都是盡力而為：不經一般網路介面的連線、把資料塞進 UserDefaults 或 Keychain，字串掃描抓不完整 | 三層檢查加審查 agent；實測時作者在實機開飛航模式跑一輪。之後若發現漏網的寫法，補進 `check-boundaries.py` |
| 設定 b 的唯讀跨模型審查，目前沒有現成工具確定可用 | 階段 1 先查 `ai-review`；沒有就用 `codex exec` 唯讀 sandbox |
| phase-workflow 的 STOP 被規則 1 自動略過後，漏掉原本該由人發現的規劃問題 | 根文件仍由 sub-agent 審；實測時觀察規劃產物的品質，必要時把特定 STOP 改列例外、翻成產品問題問使用者 |
| 範圍限制被使用者繞過（例如把「同步」說成「備份到雲端」） | 判斷依據是功能會不會把資料送出這支手機，不看使用者用什麼字；實測時刻意換說法試一次 |

訪談沒有直接問到、寫文件時從既有決策推出來的，作者 2026-09-21 全數確認：
