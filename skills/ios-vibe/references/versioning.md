# 存檔、回退與資料格式

vibe coder 多半不會 git，只會說「回到剛剛能用的版本」。你替他管版本，但**永遠不刪歷史、不丟他的改動**。

## 絕對不跑的指令

`git reset --hard`、`git checkout -- <路徑>`、`git restore`、`git clean`、`git stash drop`、`git push --force`、`git branch -D`。需要類似效果時，用下面「回到上一版」的做法。

## 開工

<!-- touchpoint: ios-vibe-010 kind=product -->
1. 專案不是 git repo：`git init`，把現況存成第一個 commit（`new-app.py` 建的專案已經做好）。
2. 工作區有使用者自己的未存改動（`git status` 不乾淨，而且不是你這次造成的）：**不碰**。白話問：「有一些改動還沒存起來，要我先幫你存一份嗎？」使用者同意才 commit；不同意就停下來，不在髒的工作區上開工。
3. 從主線開一條工作分支：`vibe/<YYYYMMDD>-<英文簡稱>`。

## 存檔點

每到一個「build 成功、測試全過」的狀態，就在工作分支 commit 一次。commit 訊息用白話寫這一步做了什麼（例如「新增：記帳可以選分類」）。

## 使用者說 OK

使用者對試用卡回 OK：把工作分支併回主線（`git merge --no-ff`），連同這張卡之前還沒併的地基類 ticket。工作分支保留，不刪。下一件事再開新的工作分支。

## push

<!-- touchpoint: ios-vibe-012 kind=product -->
- 沒有遠端：不主動建議開 GitHub。使用者問起備份，照實說明「現在所有版本都存在這台電腦上」，要不要設遠端由他決定。
- 有遠端：一律先問「要把目前的版本上傳到 <遠端名稱> 嗎？」，說好才 push。永遠不 force push。

## 回到上一版

1. 列出最近幾個存檔點，用 commit 訊息的白話描述給使用者選；使用者只說「回到上一版」時，預設是上一個存檔點。
2. **先檢查這段期間有沒有跨過資料格式升級**（見下）。有的話，先講清楚會遺失什麼，確認才繼續。
3. 從目標存檔點開一條新分支 `vibe/<YYYYMMDD>-back-<簡稱>` 繼續工作。原本的分支保留，想回來隨時回得來。
4. 重新 build 並裝到模擬器（有裝實機的話也裝一次），讓使用者看到退回後的樣子。

## 資料格式

git 只退得回 code，退不回手機裡已經升級過的資料，所以資料格式另有規則。

### 唯一的儲存方式

- 所有 app 資料都存在 SwiftData，資料庫放在範本指定的資料根目錄。
- 使用者產生的檔案（例如照片副本）只能透過範本提供的資料根目錄存取介面，存在資料根目錄底下。
- UserDefaults 只准存介面偏好（key 一律以 `ui.` 開頭），不備份，丟了也不影響使用者的資料。
- 禁止：直接用 Core Data 或 SQLite、在資料根目錄以外寫檔、把使用者資料放進 UserDefaults 或 Keychain。`check-boundaries.py` 會抓大部分，抓不到的由審查 agent 補看。

### 允許與不允許的格式變更

- **允許**：新增欄位（一定要帶預設值）、新增資料種類。資料格式版本號加一，照 SwiftData 的版本化 schema 寫升級步驟。
- **不允許**：改名、刪欄位、改型別、拆開或合併資料種類。需求需要這類變更時，照 `journeys.md`「超出範圍的需求」處理：改成用新增欄位的方式做，或找工程師接手。

### 自動備份與還原（範本已內建）

- app 啟動時發現資料格式要升級，會先把整個資料根目錄複製成以版本號命名的備份，再升級。
- 舊版 app 啟動時發現資料版本比自己新、讀不懂，會自動還原它那一版的最新備份，並在畫面上提示使用者。

<!-- touchpoint: ios-vibe-011 kind=product -->
### 跨過升級的「回到上一版」

退回的目標存檔點比最近一次格式升級還早時，先白話告知並等確認：

> 「退回去之後，app 會改用升級前留下的資料備份。<升級的日期>之後新增或修改的資料會不見（目前的資料會另外保存，不會被刪掉）。要退嗎？」

使用者確認才照「回到上一版」做；裝到手機後，請他打開 app 確認提示有出現、資料是升級前的樣子。
