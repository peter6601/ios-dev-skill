# 驗證、審查設定與試用卡

## 分工

| 誰 | 做什麼 |
|---|---|
| 你（AI） | build、跑單元測試與 UI 測試、跑邊界檢查、截改前改後的圖 |
| 使用者 | 只有實機試得出來的部分（相機、麥克風、本機通知、震動回饋、手感），以及「這是不是我要的」 |

你做得到的驗證不交給人。使用者沒有 iPhone 時，試用步驟改在模擬器上做。

---

## 出卡前的驗證清單（全過才出卡）

1. **build 成功**。
2. **單元測試全過**。
3. **UI 測試全過**：每個行為類改動，都把主要流程寫成專案 UI 測試 target 裡的 XCUITest。UI 測試一律帶 `VIBE_BLOCK_NETWORK=1` 啟動 app（範本已設好），app 只要發出任何網路請求就會失敗。累積下來的 UI 測試每張卡前全部重跑，就是回歸測試。
   指令：`xcodebuild -project <App>.xcodeproj -scheme <App> -destination 'platform=iOS Simulator,name=<iPhone>' test`
4. **邊界檢查 0 命中**：`python3 <本 skill 目錄>/scripts/check-boundaries.py <專案路徑>`。它檢查不連網、相依白名單（預設是空的：不准加任何第三方套件）、唯一的儲存方式。命中代表範圍被越過，照 `journeys.md`「超出範圍的需求」處理，不要想辦法繞過檢查。
5. **強制測試**：這次改動碰到下表任何一類，對應的測試一定要有、而且通過。

| 改動碰到 | 一定要有的測試 |
|---|---|
| 存資料 | 寫入後重建儲存層（模擬關掉 app 再打開），資料一致；只經由 SwiftData 與資料根目錄寫入 |
| 新增欄位或資料種類 | 用上一版格式的資料當輸入，升級後一筆不少、內容正確；升級前的自動備份存在，還原後等於升級前 |
| 刪除 | 只刪到該刪的那筆。刪除要不要確認、能不能復原是產品決策，照 `touchpoint-rules.md` 規則 2 問 |
| 權限（相機、麥克風、相簿、通知等） | 使用者拒絕權限時不閃退，並顯示說明與前往設定的路徑 |
| 背景或同時進行的工作 | 快速重複觸發、取消後重試，資料不重複、不寫壞 |

6. **審查**：`ios-dev` 規定的審查 agent 都跑過，發現的問題統一修完，修完再跑一次 1–5。設定 b 另加 Codex 唯讀審查（見下）。

任何一項沒過，不出卡，也不跟使用者說「好了」。修到過為止；同一個問題修三次還不過，照 `ios-investigate` 停下來找原因。

## 模擬器工具：有哪個用哪個

強制驗證只靠上面的 `xcodebuild test` 與邊界檢查，不依賴下表的任何工具。下表的工具用來截圖、看畫面，也讓使用者能即時看著 app 被操作。

| 環境 | 用什麼 |
|---|---|
| Claude 桌面 app | 內建的 iOS Simulator 面板：開工時就先打開，讓使用者看得到 |
| Claude Code 終端機 | XcodeBuildMCP（截圖、點擊） |
| Codex 桌面 app／CLI | OpenAI 官方 Build iOS Apps plugin（內含 XcodeBuildMCP，桌面 app 能顯示模擬器畫面） |
| 以上都沒有 | `xcrun simctl io booted screenshot <檔名>` 截圖 |

## 審查設定 a／b

<!-- touchpoint: ios-vibe-007 kind=product -->
第一次使用時問一次，寫進 `docs/vibe-decisions.md` 的設定區：

| 設定 | 內容 |
|---|---|
| **a（預設）** | 由你派 sub-agent 審；`ios-dev` 的 review 路線固定走 B（純 agent） |
| **b（更仔細）** | 在 a 之外，再加一次唯讀跨模型審查：Codex 只讀這次的改動、提出意見，你依意見統一修一次。不走 `ios-dev` 的路線 A，沒有 `approve-code` |

- **只有「主力是 Claude、而且裝了 Codex」才提供 b**。其他環境直接說明：「你的環境只能用 a：<因為沒有另一個 AI／你用的就是 Codex，請它審等於自己審自己>。」
- 問法範例：「每次改完，我都會派另一個 AI 分身檢查。要不要再請另一家公司的 AI（Codex）也看一次？會比較仔細，但每次多花一些時間，而且要用你的 ChatGPT 帳號。」
<!-- touchpoint: ios-vibe-008 kind=product -->
- **高風險改動時再提一次 b**（設定是 a、而且環境能用 b 時）：這次改到存資料的方式、會刪東西、要新的權限、改到同時進行的背景工作。講清楚多了誰在看、會多花時間。使用者這次要，只套用在這一次，不改設定。
- **b 的順序**：實作 → 審查 agent（a 的部分）→ Codex 唯讀審查 → 統一修復一次 → 出卡前的驗證清單 → 存檔 → 試用卡。
- **Codex 唯讀審查怎麼跑**：先看 `ai-review` 有沒有不帶 `approve-code` 閘門的唯讀 code 審查模式，有就用；沒有就用 `codex exec` 在唯讀 sandbox 跑一次，請它對這次的 diff 列出問題，只讀不改。第一次選 b 時，Codex CLI 沒裝或沒登入，就帶使用者裝好、登入（登入要他自己做）。
- **b 只作用在 code 審查**。計畫與文件的審查一律由同一個 AI 的 sub-agent 做。

## 試用卡格式

<!-- touchpoint: ios-vibe-009 kind=product -->
```markdown
## 試用卡：<這次做了什麼，一句話>

**做了什麼**
1. <白話，不出現檔名與程式名詞>
2. …
3. …

**改前 → 改後**
<截圖：改前> → <截圖：改後>
已經自動點過：<流程，一句話>

**請你在 iPhone 上試（約 N 分鐘）**
1. 打開 app → …
2. 點「…」→ 應該看到 …
<這次有改到存資料時，固定加這一步：把 app 完全關掉再打開，剛剛的資料還在嗎？>
（最多 5 步，含上面那一步）

**最可能出問題的地方**
- <例如：相簿權限被拒絕時按匯入>

**這份改動的檢查狀況**
沒有人類讀過這份 code。審查的是 AI：<實際派出的審查，白話列出，例如「畫面與互動、錯誤狀況、資料安全」>。
<有碰到強制測試時：已確認 <白話，例如「關掉再打開，資料不會不見」>。>
<設定 a：沒有另一個 AI 模型交叉檢查。>
<設定 b：另一個 AI 模型（Codex）也看過這次的改動，它的意見已經修正。>
<複雜 bug 在設定 a：這是比較複雜的修正，只有同一個 AI 審過。>

試完請回「OK」。哪裡不對，直接描述你看到的（例如「按了沒反應」）。
想回到上一個能用的版本，說「回到上一版」就好。
```

- 步驟超過 5 步，代表這次改太多，拆成兩張卡。
- 截圖用上面「模擬器工具」拿得到的工具；一張都拿不到時，改用一句話描述畫面，並註明「這次沒有截圖」。
- 修 bug 的卡，「做了什麼」要寫：原本會怎樣、現在應該怎樣；試用步驟就是原本出問題的步驟。
- 地基類 ticket 不出卡，在下一張卡的「做了什麼」補一句（例如「也先整理了存資料的方式，為之後的分類功能做準備」）。

## eli5 圖解

只在這次改動牽涉使用者必須懂的概念時（例如資料存在哪、為什麼要跟使用者要權限），才另外用 `eli5` plugin 產一頁圖解，連結放在卡片最後。不預設產生。沒有這個 plugin（例如在 Codex 上）就用三句以內的白話說明代替。
